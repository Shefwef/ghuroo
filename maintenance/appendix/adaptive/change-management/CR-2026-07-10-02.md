## Problem statement

`api/index.js` hardcodes the CORS allow-list to exactly one origin per
`NODE_ENV`:

```js
origin: process.env.NODE_ENV === 'production'
  ? ["https://ghuroo.onrender.com"]
  : "http://localhost:5173",
```

This is **not a bug in the current environment** — Ghuroo is deployed to
exactly one Render URL today and the code works correctly for it. It is a
textbook adaptive-maintenance situation (IEEE 14764: modify the system to
keep it usable as its environment changes): the moment the operating
environment changes — a custom domain is attached, a staging subdomain is
added, or the client is ever hosted separately from the API (e.g. a Vercel
preview URL hitting the Render API) — every one of the 27 files / 50
`fetch("/api/...")` call sites in the client (see
`../dependency-graph/client-dependency-graph.json` and the fetch-site count
in `MAINTENANCE_REPORT.md` Part B §3) starts failing with a browser CORS
error, with no server-side code change possible without a redeploy.

A secondary, related environment-coupling risk: `package.json` has no
`engines` field, so Render's Node-version auto-detection is free to change
between deploys as Render's own default LTS advances — `firebase-admin`
already declares `"node": ">=18"` (see
`MAINTENANCE_REPORT.md` Part B §1), so an ungoverned downgrade is a plausible
future breakage this change also forecloses.

## Root cause

Deployment target was hardcoded at the point the CORS middleware was written
(commit history: "Fixed CORS configuration" — i.e. this was already patched
once, from an even more permissive prior state, but patched to a single
literal rather than a configurable list) instead of being read from the
environment, and no `engines` constraint was ever declared.

## Fix

1. `api/index.js`: `origin` is now resolved from `ALLOWED_ORIGINS` (a
   comma-separated env var), falling back to the exact previous hardcoded
   defaults when unset — zero behaviour change for the current deployment.
2. `package.json`: added `"engines": { "node": ">=18" }`, matching the
   strictest floor actually declared among direct dependencies
   (`firebase-admin`).
3. Added `api/.env.example` documenting the full environment contract
   (previously undocumented beyond the README's prose list, which had already
   drifted — see reverse-engineering findings).

## Impact analysis summary (full detail in `MAINTENANCE_REPORT.md` Part B §3)

- Client: **zero changes needed** — confirmed by black-box-scanning the
  compiled production bundle for hardcoded backend origins (none found; see
  `../reverse-engineering/minified-bundle-blackbox-scan.md`). The client only
  ever issues same-origin relative `fetch("/api/...")` calls.
- Server: change is isolated to one middleware registration in `api/index.js`;
  `madge` confirms `api/index.js` has no other importers to consider (it's
  the entrypoint).
- Deployment: no redeploy is *required* for existing behaviour to keep
  working (default matches old hardcoded value); a redeploy is only needed
  the day `ALLOWED_ORIGINS` actually needs a second entry.
