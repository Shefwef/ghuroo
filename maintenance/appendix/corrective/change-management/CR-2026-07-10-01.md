## Problem statement

`GET /api/tours/search/:term`, `GET /api/tours/location/:location`, and
`GET /api/blogs/search/:term` build a MongoDB `$regex` filter directly from the
raw URL parameter:

```js
{ title: { $regex: term, $options: "i" } }
```

`term` is neither validated nor escaped. Because Mongo compiles `$regex`
strings as PCRE patterns using the same metacharacter rules as JavaScript's
`RegExp`, two failure modes exist:

1. **Crash / 500** — search terms containing invalid regex syntax (e.g.
   `C++ tour`) throw `SyntaxError: Invalid regular expression`, which the
   route's `catch` block converts into a generic 500 response instead of the
   intended "no results" behaviour.
2. **ReDoS (CWE-1333)** — a crafted term using nested quantifiers (e.g.
   `(a+)+$`) triggers catastrophic backtracking. Measured locally (see
   `../profiling/redos_impact_summary.txt`): a single match against a
   26-character crafted subject takes **~2.1 seconds**, doubling roughly every
   two characters added. A modestly longer term (~34 chars) would tie up a
   request for minutes — a trivial, unauthenticated denial-of-service.

## Root cause

Missing input sanitization at the point user input crosses into a
regex-interpreting sink (classic taint-flow defect — see AST trace in
`../ast/searchTours-original.ast-walk.txt`).

## Fix

Added `api/utils/escapeRegex.js` (escapes RegExp metacharacters) and applied
it at all three call sites before the value is interpolated into `$regex`.
Behaviourally: `+`/`(`/`[`/etc. in a search term are now matched literally
instead of as regex operators — the correct behaviour for a "search box" text
match, and it removes both failure modes above. No API contract change
(same request/response shape).
